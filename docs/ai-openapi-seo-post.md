# 让 AI 直接帮你查 DNS、改解析：自托管域名管理工作台的 OpenAPI 接入

> 说明：本文为「域名管家」项目的 SEO 长文成稿，可直接发布到掘金 / 公众号 / 知乎 / 个人博客。文内所有接口与能力均为项目现有实现，命令可直接复现。

---

## 开头：你还在手工一个个登云控制台查 DNS 吗？

做运维的人都知道这个场景有多烦：手里几十个域名，分散在阿里云、腾讯云、GoDaddy 好几个账号。要查某个域名解析到哪，登一个控制台；要改条记录，再登另一个；想批量看看哪些域名快到期，只能翻表格。

工具多了，人却更累了。

现在的 AI 助手已经能写代码、能读文档、能调接口，为什么它不能**直接帮你把域名和服务器管起来**？答案是可以的——前提是，你得给你的工作台开一个「AI 能读懂、能调用」的口子。

这篇文章讲一个自托管方案：如何让你自己的 AI 工具，用自然语言直接查 DNS、看健康状态、甚至改解析记录。全程自托管、密钥本地保存、权限可细分。

---

## 一、为什么是「自托管 + AI 接入」？

先讲清楚两个前提：

**1. 为什么不用现成的云控制台？**
云控制台是给人看的，不是给程序看的。它们要么没有公开 API，要么 API 授权模型复杂、按账号隔离，AI 很难统一操作「多个账号」的资产。而一个自托管的聚合层，可以把你所有云账号的域名收进一个统一界面，再统一暴露成 AI 能调的接口。

**2. 为什么 AI 需要「接口契约」而不是「网页」？**
AI 工具操作网页（点按钮）又慢又脆，一改版就失效。真正的做法是给 AI 一份**机器可读的接口契约**（OpenAPI 描述），让 AI 像调用普通 API 一样精确、可靠地操作你的资产。这也是当下 AI Agent / MCP 类工具的标准做法。

---

## 二、一个「AI 原生」的自托管工作台长什么样

以开源的**域名管家（Domain Manager）**为例，它是一个 PHP 全栈自托管工具，聚合阿里云 / 腾讯云 / GoDaddy 多账号域名，自带健康看板、资产关系图、DNS 管理、到期提醒。最关键的是，它从设计上就做了 AI 接入——不是事后补丁，而是产品能力。

它对 AI 暴露了三个东西：

| 端点 | 作用 |
|---|---|
| `GET /api/openapi.json` | 机器可读的 **OpenAPI 3.1 接口契约**，AI 据此知道能调哪些接口 |
| `GET /llms.txt` | 面向 AI 的自然语言操作说明，告诉 AI 怎么用、注意什么 |
| `GET /.well-known/asset-workspace.json`（或 `/api/capabilities`） | **能力发现**，让 AI / 工具自动识别这个工作台的能力 |

配合 **Bearer Token 鉴权 + 分权限密钥**，AI 只能用它被授权的 scope，动不了不该动的。

## 三、实操：三步让你的 AI 接管域名资产

> 以下命令基于项目 `scripts/workspace-api.py` 与产品配置，均可直接复现。完整配置说明见项目的 `docs/product-and-api.md`。

### 第 1 步：安装并生成 API 密钥

安装后进入「产品设置 → AI API」，创建一个有**有效期、分权限**的密钥。scope 分得很细：

| scope | 能力 |
|---|---|
| `assets:read` / `assets:write` | 读取 / 增改删本地资产与人工绑定 |
| `dns:read` / `dns:write` | 读取缓存 / 云端 DNS 增改删 |
| `checks:run` | 执行健康与访问检查 |
| `sync:run` | 同步云端域名及测试账号 |

默认只勾选最安全的 `assets:read` 和 `dns:read`——**AI 默认只能读，不能改**。需要写权限时再显式放开。密钥最长有效期 365 天，随时可撤销。

### 第 2 步：把工作台地址和密钥交给 AI

```sh
export WORKSPACE_URL='http://127.0.0.1:8080'
export WORKSPACE_API_TOKEN='你在产品设置创建的密钥'
```

然后就能像调普通 API 一样查询：

```sh
# 查所有域名
python3 scripts/workspace-api.py GET /api/domains

# 查健康状态
python3 scripts/workspace-api.py GET /api/health
```

或者直接 curl，走标准 Bearer 鉴权：

```sh
curl "$WORKSPACE_URL/api/health" \
  -H "Authorization: Bearer $WORKSPACE_API_TOKEN"
```

> 注意：`127.0.0.1` 仅供运行在同一台机器的 AI / 脚本使用；远程部署时应通过 HTTPS 提供服务，并把 `Authorization` 请求头正确转发给 PHP。

### 第 3 步：让 AI 学会「先查后改」的规范操作

域名管家给 AI 的操作路径是清晰的，这也是写进 `llms.txt` 的约定：

1. **先读** `/api/domains` 拿到域名和 `provider`（云账号 ID，例如 `aliyun_1`）——注意不能用 `aliyun` 这类云商类型代替。
2. **再读** `/api/domains/{provider}/{domain}/records` 拿到记录 ID。
3. **改** 记录时调用 `PUT /api/domains/{provider}/{domain}/records/{recordId}`，传 `type`、`name`、`value`、`ttl`、`priority`、`line`，**保留不需要修改的字段**。该接口真正修改云端 DNS，需要 `dns:write`。

这样 AI 的每一次操作都有据可查、可审计，不是黑盒点按钮。

## 四、安全边界：这是关键

AI 能操作资产，安全必须跟上。域名管家把安全设计成了产品的一部分：

- **密钥分权限、有有效期**：`assets:read` 和 `dns:read` 默认只读，写操作显式授权；密钥到期自动失效。
- **密钥本地保存、不回显**：云凭据存放在站点目录之外的私有 JSON 文件，不通过查询接口回显；密钥明文只在创建响应返回一次。
- **写操作全程校验**：登录 Session + `X-CSRF-Token`；Bearer 请求不需要 Cookie 或 CSRF，但权限范围受 scope 严格约束。
- **健康结果不被误判**：文档明确约定 `unchecked` 和 `stale` 不能计为健康；客户端同时检查 HTTP 状态与 `ok:false`——历史云接口有时以 HTTP 200 返回业务失败。

这套「最小权限 + 可撤销 + 可审计」的模型，正是 AI 接入类工具该有的样子。

## 五、收益：AI 接入后你能少做什么

接入之后，日常工作会明显变化：

- **查询秒回**：不用登三个控制台，「我这个域名解析到哪」「哪些域名快到期」一句话搞定。
- **批量改解析**：统一在自托管层操作多账号，而不是一个个点。
- **资产影响面一眼看清**：结合资产关系图，AI 能告诉你「这台服务器挂了影响哪些网站」。
- **可被人/程序复用**：OpenAPI 契约不止 AI 能用，你的脚本、CI、自动化都能用同一套接口。
