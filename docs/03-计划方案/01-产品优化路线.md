# 产品优化路线：从资产工具到可交付产品

日期：2026-10-27。依据：当前仓库代码、README、近期界面调整及既有产品文档。本文是优化建议，未实现项不构成销售承诺；未执行真实云商写操作或生产容量测试。

> 1.1.0 已落地资产备份与预览恢复、JSON 迁移、CSV 导出、基础操作记录、部署自检、交付摘要及来源文件白名单发行包；同步失败不再刷新成功时间。完成范围和剩余门槛见 [本轮落地与后续迭代](05-本轮落地与后续迭代.md)。以下路线保留完整目标，不能把基础实现理解为全部 P0 完成。

> 1.2.0 已补齐 DNS 差异预览、旧值版本检查、写后回读与有限前后值记录，并修复同组删除及部分字段保留问题；验证使用本地云商模拟器，客户云环境验收仍是交付门槛。

## 1. 产品应该往哪里走

建议把产品收敛为：**面向多站点团队的域名与 IP 资产工作台。**

用户进入系统，应该能快速完成四件事：

1. 找到一个域名、网站或 IP，知道它的用途与归属。
2. 看清域名、子域名、IP 的关联依据，以及哪些绑定经过人工确认。
3. 找到需要处理的检查异常、临近到期和资料缺失。
4. 完成检查、资料维护或 DNS 变更后，留下可核对的结果。

现阶段继续增加大屏图表的收益有限。更值得投入的是数据可信、任务可靠、交付简单，以及异常发生后有人能处理。

## 3. 优先级怎么排

P0 是稳定收费交付前的基础，P1 是提高留存和续费的主线，P2 在有付费需求证据后投入。访谈、演示和限定范围的试点可以先做；缺少 P0 时不宣传成熟监控服务。

| 优先级 | 优化项 | 为什么值得做 | 完成标准 |
| --- | --- | --- | --- |
| P0 | 数据时间与状态口径统一 | 用户要知道自己看到的是哪次结果 | 每条状态有检查时间、证据、过期说明；统计与列表一致 |
| P0 | 备份、恢复和升级回退 | 客户交付后最怕资料与配置丢失 | 在空白实例完成一次备份恢复，核对资产、绑定、备注及授权处理 |
| P0 | 正式部署包与环境边界 | 减少每个客户都重做部署 | 固定版本、依赖清单、生产配置示例、安装和升级说明齐全 |
| P0 | 云端写入可核对 | DNS 变更影响实际网站 | 提交前预览差异，失败真实反馈，成功后回读并记录结果 |
| P0 | 生产安全与发布清理 | 产品会保存客户云凭据 | 诊断受限、初始化受控、配置不随安装包外发、日志脱敏 |
| P1 | 后台任务与调度 | 让检查不依赖浏览器开着 | 关页面后继续；重启后能识别中断任务；任务结果不重复写入 |
| P1 | 到期和异常通知 | 让客户在不打开页面时也能收到有用信息 | 首次异常、恢复、通知失败都有记录；重复异常不刷屏 |
| P1 | CSV 导入 / 导出 | 把客户 Excel 台账迁过来 | 导入前预览、重复冲突报告、逐行错误、导出可对账 |
| P1 | 项目 / 客户 / 负责人 | 从个人工具走向团队工作 | 支持归类和筛选，异常能找到负责处理的人 |
| P1 | 审计与历史 | 解决“谁改了什么”的疑问 | 记录操作者、时间、目标、前后差异及结果；不记录密钥明文 |
| P2 | 多人角色与项目授权 | 支撑团队版收费 | 服务端限制读写，跨项目读取和修改均有拒绝测试 |
| P2 | 客户报告和品牌化 | 帮代维团队向其客户交付成果 | 可输出指定客户的资产清单与巡检记录，范围不串数据 |
| P2 | AI 查询助手 / 扩展集成 | 降低特定用户的查询成本 | 先做只读摘要，展示数据时间和来源，写操作单独授权 |

最先建议实现的三个小版本：**可恢复的交付版 → 后台检查版 → 通知与处理版。** 不把数据库重构、多人权限和 SaaS 支付系统同时塞进第一版。

## 4. 界面还可以怎样精简

### 4.1 保持列表优先

延续当前“搜索与列表直接可见、筛选在搜索前、更多内容从按钮展开”的结构。统计和关系图服务于具体问题，不占据默认列表空间。

- 保存常用筛选，如“检查异常”“30 天内到期”“未确认绑定”；在按钮上显示生效条件数量，并提供一键清除。
- 列表支持列显隐与宽度记忆。按页面分别保存，避免所有用户被迫看一套宽表。
- 主操作保持少量且稳定；批量操作只在选择资产后出现，并写清“作用于当前选中 N 项”。
- “点击状态检查”保留，同时展示悬停提示和运行反馈，阻止同一资产重复提交；检查完成不让当前列表跳动。
- 弹层过长时内容内部滚动，关闭与关键操作保持可达；检查小屏、缩放、键盘与大屏下的定位。
- 空数据、没有搜索结果、加载失败、云账号权限不足分别提供下一步动作，不共用“暂无数据”。

### 4.2 少量但有用的统计

推荐固定四个指标：**需要处理、即将到期、检查已过时、尚未检查**。数字可以醒目，但每个数字都应能点击进入对应列表。

“正常率”必须说明分母。建议主指标用“已检查且未过期的目标中正常比例”，旁边另列未检查与过时数；不要把未检查算正常，也不要把单次检查结果包装成历史在线率。

页面同时显示“资产同步时间”和“最近检查时间”。点击刷新列表只读取数据，点击同步才访问云商，点击检查才执行探测，让用户理解这三个动作的区别。

### 4.3 用事实展示关系

在域名和 IP 详情中展示“关联依据、观察时间、确认人 / 确认时间”。DNS 解析得到 CDN 或代理地址时，只能说明解析关系，不能证明源站归属。

从 IP 展示的是“已登记 / 已观察到的关联站点”，而不是保证完整的故障影响面。后续增加关系变更记录，帮助用户回答“昨天还指向哪里”。

## 5. 检查逻辑的下一步

当前 IP 规则按需求保留：请求 `http://IP/`，IPv6 加方括号，2xx / 3xx 判为正常，不继续跟随重定向，结果缓存在服务器。

这个结果只说明该入口在检查时返回符合当前规则的 HTTP 响应。某些网站依赖 Host、HTTPS 或登录，裸 IP 检查异常不一定是服务器故障；3xx 也没有证明跳转后的页面可用。

建议下一阶段在不改变现有默认规则的前提下增加“网站检查目标”：

| 检查层级 | 目标与证据 | 页面表述 |
| --- | --- | --- |
| IP 入口 | `http://IP/`、状态码、耗时、检查时间 | “IP HTTP 检查正常 / 异常” |
| 网站 URL | 完整 URL、请求方法、超时、期望状态码 | “网站访问检查结果” |
| DNS / TLS | 解析结果、证书验证结果、证书到期信息 | 分项展示，不用一个绿色状态掩盖差异 |
| 业务检查（后期） | 关键词或 JSON 字段，必要时模拟业务流程 | 只承诺配置过的检查范围 |

把“网站名称 + URL”从快捷链接逐步升级为可选检查目标，能够更贴近客户管理站点的习惯。但链接保存本身不能自动代表已经监控该网站。

建议增加连续失败阈值、恢复阈值和维护窗口，避免一次网络抖动就发告警。跨地域探测与历史在线率放到后期；单节点探测先把地点、时间、采样频率交代清楚。

## 6. 从浏览器批处理升级为后台任务

建议保留现有 Controller / Service 分层，先用 CLI Worker 与定时入口复用检查服务，不为此重写整个应用。

任务应持久化任务 ID、类型、目标快照、发起人、开始 / 完成时间、逐项结果和重试次数，状态至少包含排队、运行、成功、部分成功、失败、取消。

- 页面提交后返回任务 ID，查询进度；重载页面可继续查看同一任务。
- 按云账号和目标限制并发，对超时、限流采用有上限的重试；DNS 写入不能盲目重放。
- 取消只阻止后续执行，已完成的云端变更不能描述为已撤销。
- Worker 重启后识别失联任务，决定恢复或标记中断；同一目标设置互斥，避免旧结果覆盖新结果。
- 通知作为单独可重试的发送步骤，不能因通知失败把已完成的检查重新执行一遍。
- 无 cron / 无常驻进程的环境明确降级为手动版，不宣传自动监控。

任务链路验收：提交 20 个测试目标 → 关闭页面 → Worker 继续 → 中途重启 Worker → 回到页面 → 结果与逐项目标对得上。

## 7. 数据模型与性能

### 7.1 先让数据可迁移，再决定存储

当前 JSON 适合单实例轻量使用，已有部分文件锁和原子写入机制。它不等于完整关系事务，也不能直接推导出能支持多少客户。

先为资产、绑定、检查、任务补充稳定 ID、结构版本、更新时间与来源；再按实际需要迁移到 SQLite。只有多实例并发、独立队列或更高可用要求明确时，再评估 MySQL 等方案。

迁移需要：导出旧数据 → 备份 → 迁移校验 → 读写验证 → 核对数量及关联 → 保留回退入口。不要在首个付费客户的唯一生产数据上首次试迁移。

### 7.2 分开注册管理与解析托管

域名在哪里注册、DNS 在哪里托管、由哪个账号管理，应是独立概念。不能继续用一个账号字段承担全部归属，否则跨平台解析、同域名多来源和后续接入新云商都会困难。

建议模型逐步分成：客户 / 项目 → 网站 / 服务 → 域名 / 主机名 → 解析记录 → 观察 IP；人工确认的服务器绑定单独记录。IP 地址不是长期稳定的服务器身份；地址复用和迁移时应保留历史，不把旧备注自动带给新机器。

### 7.3 性能先测量

用合成数据分别验证 100、1,000、10,000 条资产的搜索、列表、关联图和接口响应，记录机器环境、数据结构、P95 延迟和内存。它们是压测档位，不是目前支持规模的声明。

当数据量明显影响首次加载时再引入服务端分页、筛选索引和增量统计；关系图只渲染当前范围。不要为了提高上限而让所有用户默认下载和绘制全部资产。

## 8. 收费交付前的工程准备

- 提供固定版本安装包、校验值、变更日志、PHP / 扩展兼容矩阵和生产 Web 服务配置示例；开发服务器只用于本地验证。
- 首次配置在受控环境完成后再开放访问；诊断页默认受限，公开信息与管理员诊断信息分开。
- 说明云凭据保存在客户实例的私有配置文件中，目前不能宣传为“从不落盘”或“已静态加密”。后续加密应把主密钥与数据文件分离，并验证换机恢复。
- 日志、工单和导出默认排除密码、Token 与云凭据；发给客服的诊断包提供预览和脱敏。
- 备份区分普通资产导出和包含凭据的完整备份；完整备份需受保护，恢复后明确旧 Session / Token 的失效策略。
- DNS 修改记录旧值、拟提交值与云端回读结果；回读成功不等于全球解析已传播。恢复旧值仍是一次需要核对的变更。
- 补全代码与素材来源、依赖声明、授权方案；当前仓库根目录未发现 LICENSE，先确认权利范围，再决定是否公开源代码及采用何种授权。

本节已有部分基础实现：版本发行包、生产配置示例、受限诊断、资产备份与恢复流程均已落地；云凭据静态加密、完整配置备份工具、DNS 前后值与回读、权利确认和客户生产验收仍需完成。

## 9. 90 天推进建议

以下是单人或小团队的排序建议，实际排期根据访谈、技术验证和试点范围重估。

| 阶段 | 聚焦 | 可检查的产出 |
| --- | --- | --- |
| 第 1–2 周 | 能力对齐、访谈、限定范围演示 | 找 10 位目标用户，记录真实台账、现用工具、最近一次损失和报价反馈 |
| 第 3–4 周 | 可交付基础 | 固定版本包、备份恢复演练、部署说明、错误反馈与状态口径校验 |
| 第 5–8 周 | 后台检查与一个通知渠道 | 页面关闭仍可检查；异常与恢复通知可追踪；完成 2–3 家隔离试点 |
| 第 9–12 周 | 根据付费反馈深化 | 导入导出、归属字段、基础审计优先；再决定多人权限和团队版 |

如果访谈发现客户只愿意购买一次资产整理服务，就先把服务标准化；如果客户反复要求持续提醒并愿意续费，再投入监控订阅。不要仅凭“功能应该有”扩展产品。

## 10. 先不投入的方向

暂缓完整 CMDB、CPU / 内存 Agent、SSH 终端、自动重启、自动续费、复杂多租户计费和大而全的 AI 运维助手。每项都会引入新的维护与责任范围，应有真实订单或明确复用场景后再做。
