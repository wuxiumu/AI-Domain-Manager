# AI 协同与未来工作台

状态：**方向设想，均未实现**。本文基于 1.2.0 及「AI 分析报告」落地后的代码现状，给出近期优化、中期方向与长期愿景；与[产品优化路线](01-产品优化路线.md)和[本轮落地与后续迭代](05-本轮落地与后续迭代.md)互为补充，优先级冲突时以这两篇为准。

## 1. 已具备的基础

AI 协同不是从零开始，现有架构已经埋好了关键护栏：

| 已有能力 | 位置 | 对 AI 协同的意义 |
| --- | --- | --- |
| OpenAPI 3.1 + `llms.txt` + 能力发现 | `/api/openapi.json` 等 | AI 可自发现契约，无需人工粘贴文档 |
| 带范围与有效期的 API 密钥 | `assets:read` 等 6 类 scope | 最小权限，可撤销，改密即失效 |
| DNS 版本化单次写入 + 回读核实 | `expected_version` / 202 / 409 | 天然适配 agent：写一次、可验证、不重试 |
| 健康报告 + 分析提示词 | `/api/health/report` | 证据快照可直接交给任意 AI 分析 |
| 操作审计 | `audit.json` / DNS 变更前后值 | 每一步 AI 动作可回溯 |

## 2. 近期优化（现有架构内）

按「减少交付工时、避免资料丢失」的既有取舍排序：

1. **报告对比（diff）**：报告接口支持与上一份存档对比，只输出变化行。管理员每天看的是「变了什么」而不是全量；AI 分析的上下文也更短。
2. **证书到期台账**：HTTPS 检查已校验证书，但到期天数没有沉淀为台账。把每次检查的证书到期时间写入健康状态，看板增加「证书 30/60/90 天到期」筛选，复用现有 30 天域名到期逻辑。
3. **定时脚本泛化**：`scripts/check-domain-operations.php` 扩展为可选检查 IP 与子域名、检查后可选输出报告（含 `--prompt`），让现有 cron 一次性产出「晨报」。
4. **大库存性能**：`/api/health` 随资产线性增长（含子域名数组）。超过数百资产后考虑列表分页或瘦身字段；前端 `renderRows` 每次按键重建整表，可加输入防抖。（2026-11-06 部分落地：`/api/health` 列表不再内嵌检查历史，历史改存 `data/history/` 按资产小文件并由 `GET /api/health/history` 按需读取；主文件改为紧凑编码；前端搜索防抖与批量检查节流重绘已加；接口支持 ETag/304。分页/虚拟滚动仍未做。）
5. **静态契约缓存**：`/api/openapi.json`、`/llms.txt` 只随版本变化，可加 `ETag` / `Last-Modified`，减少 AI 工具轮询开销。（已落地 2026-11-06：契约与健康、域名列表接口均支持 ETag/304。）
6. **报告快照留档**：生成的报告按日留档（如保留 30 份），为后续 diff 与「昨天 vs 今天」分析做数据准备。

## 3. 中期方向

### 3.1 后台检查 + 通知（已规划，报告融入）

后台任务与通知渠道在[迭代计划](05-本轮落地与后续迭代.md)中列为下一轮。落地时把报告生成挂进同一管线：每日检查完成 → 自动生成报告 → 推送（邮件 / Webhook / Bark 等）。管理员与 AI 拿到的是同一份证据，口径一致。（2026-11-06 前置落地：任务队列 `POST /api/tasks` + `scripts/task-worker.php` cron worker 已可用，支持全量健康检查、访问检测与同步的后台执行与心跳恢复；通知渠道与报告推送仍待做。）

### 3.2 MCP Server：从「给报告」到「接进工具」

在现有 OpenAPI 之上包一层 Model Context Protocol 端点，把「列资产、看健康、读报告、（经批准）写 DNS」注册为 MCP 工具。Claude 等客户端即可原生调用，`llms.txt` 与 MCP 描述共享同一份文案源。工作量集中在协议适配，业务与护栏全部复用。

### 3.3 AI 行动提案队列（已落地，人在环上）

已实现（2026-11-02）：AI 密钥以 `proposals:write` 提交提案（`POST /api/proposals`，含变更理由与依据，重复待审批提案 409，待审批上限 50 条）；管理员在「数据与交付 → AI 变更提案」批准或拒绝；批准时读取云端最新版本、按既有护栏单次写入并回读核实；目标消失或账号不可用时标记 failed 并保留原因。`GET /api/handover` 提供接管交接简报（统计、持有权限、行动序列）。`GET /api/proposals`（`proposals:write`）供 AI 跟踪状态。

后续增强方向：提案引用健康报告的具体行并自动校验依据仍然成立；批准前自动重跑目标资产检查以确认提案仍然必要；同账号多提案的批量批准与顺序执行。

### 3.4 监控平台对接（已落地，共同治理）

已实现（2026-11-02）：`GET /api/metrics`（`assets:read`）以 Prometheus 文本格式输出 `asset_workspace_*` 指标——资产分布、HTTPS 未确认数、30 天检查量与平均延迟、AI 提案状态、最近检查时间戳；监控平台可用现有 API 密钥直接抓取，接入既有告警与大盘。「检查趋势」独立页面渲染近 30 天检查趋势图（`GET /api/trends`，内联 SVG、无外部依赖）。分工原则：人看图表做判断，AI 经 HTTP 执行操作（提案审批为写入闸门），监控平台读指标做告警——三方共用同一份缓存证据。

后续增强方向：按资产维度的指标标签（当前仅全局汇总）；趋势窗口可配置；异常恢复事件流（供 webhook 推送）。

### 3.5 台账迁入与生命周期

CSV 逐行预览迁入（已规划）之后，自然延伸是生命周期时间线：域名续费、证书到期、服务器租约到期统一成一条可筛选的时间轴，替代分散在各列表的到期字段。

## 4. 未来的工作台什么样

三条主线叠加后的终态画面：

**值守式，而非查询式。** 打开工作台第一眼不是资产列表，而是「今天需要处理什么」：夜间检查已完成，晨报列出新异常、即将到期的证书与域名、AI 给出的归因与建议；异常恢复也会主动通知。工作台从「台账」升级为「值班员」。

**AI 在环上，人在决策位。** AI 值班员持续读证据、出提案；所有变更动作停在提案队列等待批准，批准后仍走版本核对与回读。审计里每条记录都能回答「谁批准、依据哪份报告哪一行、结果如何」。信任来自护栏，不来自放权。

**一条生命周期时间线。** 域名、证书、服务器、DNS 变更历史在同一条时间轴上；任何资产点进去都能看到「检查证据 + 关联资产 + 变更履历」。交接时导出的不再是一堆表格，而是这份完整履历。

不变的定位：单管理员、可自行部署、数据在本机、缓存优先、最小权限。所有 AI 能力都建立在这五条之上，而不是替代它们。

## 5. 暂不投入

沿用[产品优化路线](01-产品优化路线.md)第 10 节结论，并补充：不做内置聊天窗口（`llms.txt` + 外部 AI 已覆盖，避免重复实现安全边界）；AI 直接写 DNS 不设审批（提案队列是唯一路径）；不自建通知中台（接一个渠道验证价值即可）。
