# 商业化方案：先卖交付结果，再验证持续订阅

日期：2026-10-27。状态：商业验证方案。文中客群、价格、成本和转化目标均为待验证假设，不是市场成交数据；未在本轮创建收费、授权、支付或订阅功能。

## 1. 我的建议

**第一阶段卖“客户自有服务器上的资产工作台部署 + 资产整理 + 使用交接”。** 优先找建站、代维、小型开发团队，用清晰的实施范围获得首批订单。

卖点应围绕客户每天遇到的事：域名散落在不同账号，IP 的用途记不清，交接依赖某个人，准备迁移时不知道关联哪些站点。多账号台账、人工绑定、备注和网站入口能够共同解决这些问题。

监控订阅、团队协作和服务商品牌版是后续增长方向，需要先补功能并证明持续付费意愿。AI 接口作为技术加分项，先不作为唯一购买理由。

## 2. 第一批客户选谁

| 人群 | 值得解决的问题 | 购买动机假设 | 当前适合卖什么 |
| --- | --- | --- | --- |
| 建站 / 代维团队，维护多个客户站点 | 客户站点、域名、云账号和 IP 分散，交接费时 | 降低查找和交接成本，形成自己的服务台账 | 独立部署、资料整理、后续迁移支持 |
| 小型企业技术负责人 | 资产资料依赖 Excel 和个人记忆 | 资产可查、操作有据，便于交接 | 单管理员私有化试点 |
| 个人站长 / 独立开发者 | 多账号域名和网站入口难整理 | 自己用得顺手、安装省事 | 自部署或小额部署服务；不把他们当高客单价主力 |
| 中大型企业 / 强合规团队 | 多部门权限、审批、审计、统一身份 | 组织治理与风险控制 | 先访谈；当前不承诺企业完整替代方案 |

建议访谈时优先筛选“最近确实发生过资产交接、迁移、找不到账号或续费遗漏”的人。维护站点数量只是线索，发生过的具体问题更能说明需求。

可以先假设客户有 20–200 个域名、几个云账号，但这仅用于找人，不代表产品经过这个规模的性能认证。

## 3. 定位和差异化

推荐对外名称先统一为：**资产工作台｜域名与 IP 管理**。保留“域名管家”作为历史项目名称或搜索关键词；先不为改名投入大量时间。

一句话定位：

> 为多站点团队整理域名、IP、网站入口和关联资料的私有化工作台。

主价值按这个顺序讲：**找到资产 → 看清关联 → 检查状态 → 完成交接。**

### 与现有工具的关系

下面仅比较官方公开的产品重点，不是完整功能测评，也不宣称任何一款工具没有其他能力。

| 工具方向 | 官方资料体现的重点 | 对本项目的启发 |
| --- | --- | --- |
| Uptime Kuma | 自托管、多种探测、通知和状态页 | 单纯“自托管 + 网站检查”已有成熟选择，不宜只靠这个收费。[官方仓库](https://github.com/louislam/uptime-kuma) |
| Better Stack Uptime | 可用性监控、事件处理、告警和状态页 | 持续监控的客户预期包含通知与处置过程，不能把手动检查包装成同等能力。[官方产品页](https://betterstack.com/uptime) |
| DNSControl | 多 DNS 服务商的配置管理、代码化与版本管理 | 深度 DNS 自动化可考虑集成或借鉴流程，不必一开始自己做完整 GitOps。[官方文档](https://docs.dnscontrol.org/) |

因此，我的判断是：本项目更适合从“资产资料与站点关联的日常工作入口”切入，逐步串联检查和处理流程。这个定位需要客户验证，不使用“行业唯一”“同类极少”“AI 原生最大差异化”等缺乏证据的宣传。

## 4. 当前能卖到什么程度

当前可以演示和限定范围交付：多云账号域名管理、DNS 操作、域名与 IP 关联、手动检查、备注、网站快捷链接、私有化部署及分权限 API。

1.1.0 已补齐资产备份与预览恢复、JSON 迁移、CSV 导出、基础操作记录、环境自检、交付摘要及来源文件白名单发行包。实施时可把这些功能直接作为交接流程，而不是承诺以后补。

正式收费交付前仍要逐项核对 [产品优化路线中的 P0](01-产品优化路线.md#3-优先级怎么排)：DNS 差异与回读、客户环境恢复演练、生产访问控制、完整实例备份与代码素材权利尚未全部完成。第一批客户采用书面限定范围、可验收的单实例试点。具体边界见 [本轮落地](05-本轮落地与后续迭代.md)。

当前不能当成现成功能出售：

- 全天候后台监控、自动到期提醒、邮件 / 飞书告警、自动故障恢复。
- 多人分角色、多客户工作区隔离、SSO、完整操作审计。
- 已内置的自然语言 AI 助手、AI 自动修复、任意 AI 工具开箱即用。
- 任意云商全兼容、无限资产、已验证的服务可用性承诺。

可以销售独立的需求评估和定制开发服务，但要单独列出范围、开发期及验收条件，不能让客户把路线图理解为当前授权已经包含的能力。

## 5. 收费结构建议

早期只公开一个主套餐和一个维护选项，降低客户比较成本。下面是人民币含义明确的试报价示例；是否含税、支付条件和正式服务条款在真实报价时确认。

| 套餐 | 建议试报价 | 范围 | 销售状态 |
| --- | --- | --- | --- |
| 私有化部署与资产整理 | ¥1,499 / 次 | 一个客户、一个实例、最多 3 个现有受支持云账号接入、最多 50 条客户已整理资料的人工录入协助、一次 30 分钟交接；实施总投入上限 4 小时 | 完成 P0 后用于首批试点；超范围另估 |
| 年度维护服务 | ¥999 / 实例 / 年 | 两次计划内版本升级协助及问题排查，全年远程服务累计不超过 2 小时；每次先备份 | 完成基础交付后可选，不等于监控代维 |
| 团队增强版 | ¥1,999 / 实例 / 年起，作为意愿测试锚点 | 计划提供后台任务、一个通知渠道、变更差异追踪及最多 3 名成员；容量与检查频率经测试后定义 | 规划，不作为现成订阅收款 |
| 定制集成 | ¥8,000 起，先评估再报价 | 指定云商适配、内部系统对接、特定报告或业务流程；逐项列验收 | 单独开发合同，不承诺任意需求统一价格 |

“50 条资料”指手工整理协助的服务上限，不是软件资产数量限制；也不表示当前已有 CSV 导入。云端域名同步的数量与完整性在接入验收中单独核对。

不要轻易卖终身维护、无限客户、无限工单。一次性交付费用、软件使用授权、未来版本权益和人工维护是不同内容，报价单分别写清楚。未开通未来订阅不应锁住客户已有的资产导出和备份。

### 如何调整价格

先拿相同范围向 5 位合适客户报真实试点价，记录成交与拒绝原因。不要只问“你觉得多少钱合适”，要确认是否愿意按这个范围启动。

- 如果频繁成交但实施工时超标，先缩小基础服务范围，再考虑提价。
- 如果客户只需要部署，保留一次性方案；没有持续价值就不硬推订阅。
- 如果客户集中要求提醒，先交付一个可靠通知渠道，再验证年度续费。
- 如果同一增量需求被 3 家独立付费客户提出，优先评估产品化；仅一家需要的复杂改动按定制处理。

## 6. 算清交付能否赚钱

用真实工时核算，先不把自己的时间当免费。

单笔贡献的简化算法：**实收 − 实施工时成本 − 获客成本 − 售后预留 − 外部直接费用**。固定研发、税费及其他经营费用需另外计入，不能把贡献直接当净利润。

举例：¥1,499 实收，4 小时 × ¥200 的内部成本、¥200 获客成本、¥100 售后预留，无其他直接费用，则单笔贡献约 ¥399。若每单实际用 8 小时，这个报价就需要调整。

每单记录实施、迁移、培训、售后四类工时。年度维护若多次超出 2 小时上限，应升级服务档位或另报价，不靠无限免费排查维持关系。

资产量并不是唯一成本因素；云商接入复杂度、检查频率、通知渠道、客户数量和数据隔离要求都可能增加成本。后续订阅套餐应同时写清这些边界。

## 7. 开源、源码和 SaaS 如何选择

当前根目录未发现 LICENSE。应先整理代码、图标、字体和其他素材的来源及可分发范围，再决定产品授权；本方案不自动授予任何权利，也不替你选择许可证。

| 选择 | 适合情况 | 需要承担的工作 |
| --- | --- | --- |
| 暂不公开源码，先做独立客户试点 | 希望快速验证交付和收费 | 明确客户软件使用范围、更新权益、迁移与退出方式 |
| 开源基础版 + 付费交付 / 增强版 | 已有社区维护意愿，愿意公开基础代码 | 明确开源与增强版边界，持续维护文档和兼容，评估外部贡献的权利范围 |
| 共享 SaaS | 客户明确不愿自备服务器，且持续付费证据充分 | 租户隔离、凭据托管、后台任务、计费、备份、服务保障和退出机制 |

建议先采用“客户自有实例 + 有限范围实施服务”。它不要求先建设共享 SaaS 的整套平台。即便客户是代维服务商，也先用其团队内部实例；尚无隔离能力时，不能给不同终端客户共用管理员入口。

不要为了防复制先投入复杂授权服务器。等标准化软件形成复购，再评估离线授权或在线授权；授权故障时仍应保留客户读取、导出和恢复自己数据的通道。

## 8. 首批客户怎么找

优先级建议：**已有关系中的建站 / 代维团队 → 场景演示内容 → 可复用安装文档 → 社区与渠道扩展。** 相比大量泛流量，先获得几次真实工作场景反馈更有价值。

第一轮做这些事：

1. 准备一套全部为虚构数据的演示实例，展示三个账号、几十个域名及若干 IP。
2. 录制 60–90 秒演示：搜域名 → 看备注与关联 → 从 IP 找站点 → 单次检查 → 查看时间与证据。
3. 邀请 10 位符合画像的人做 20 分钟访谈，询问最近一次查资产、交接或迁移是怎么处理的。
4. 对愿意继续的 5 位客户，给出相同范围的试点报价，目标是获得 2–3 个有明确验收的付费试点。
5. 交付后复盘工时和实际使用，经过客户许可才整理匿名案例。没有结果证据时不写节省比例或收益数字。

这些数字是第一轮实验目标，不是收入预测，也不是必须完成的销售配额。本轮已实现交付基础功能，但没有联系客户、对外发布文案或收款。

### 访谈问题

- 现在怎么记录域名属于哪个账号、IP 用于哪个网站？能演示一次查找过程吗？
- 最近一次域名迁移、人员交接或续费遗漏，卡在了哪里？
- 已有的监控、云控制台、Excel 分别解决什么问题？还有哪一步要靠问人？
- 哪个功能如果没有，你就不会用？哪个功能只是看起来不错？
- 你愿意为一次整理和部署付款，还是更需要长期提醒与维护？预算由谁决定？
- 接受客户自有服务器部署吗？谁维护实例，谁保管云凭据？

避免引导式问题，例如“有这个功能是不是就能节省很多时间”。记录具体操作和实际愿意购买的范围。

## 9. 交付与售后边界

建议流程：需求确认 → 环境与资料核对 → 书面范围与报价 → 受控部署 → 客户自行填写凭据 → 对账与演示 → 验收 → 有限维护。

| 环节 | 标准产出 | 验收方式 |
| --- | --- | --- |
| 范围确认 | 实例、账号、资料、人工工时和支持时间范围 | 客户按清单确认，不把规划项混进现成能力 |
| 部署 | 指定版本、访问地址、环境说明 | 新会话可登录；只通过 public 提供网站内容 |
| 账号接入 | 凭据由客户填写，权限说明与连接结果 | 账号可识别；同步结果可对账，失败不伪装成功 |
| 资料整理 | 约定范围的域名 / IP、备注、网站链接和人工绑定 | 用客户提供的清单抽查数量与关键字段 |
| 检查演示 | 当前手动检查与缓存机制 | 单次检查时间、状态和证据更新；批量需保留页面 |
| 数据恢复 | 受保护的备份与恢复说明 | 在隔离环境实际恢复，敏感配置不经公开渠道传输 |
| 交接 | 管理说明、版本、支持方式与到期时间 | 客户自己完成一次搜索、修改备注、检查和导出 / 备份流程 |

建议首单基础服务包含验收后 7 个自然日的交付范围内缺陷反馈窗口，工作时段一个工作日内首次响应；这是拟定服务标准，上线前应确认自己能做到。首次响应不等于解决时限，不包含云商故障处理、全天候值守和客户业务可用性保障。

额外 DNS 修改、服务器迁移、网络修复和数据补录均先明确范围。客户随时能拿到自己的资产资料，退出服务时完成备份和凭据轮换交接。

## 10. 判断商业方向是否成立

| 指标 | 看什么 | 下一步判断 |
| --- | --- | --- |
| 激活 | 是否成功接入一个账号或登记首批资产，是否查到有用关联 | 卡在安装就先改交付，卡在资料就先改迁移 |
| 使用 | 客户是否在后续两周再次用它完成查找、检查或维护 | 持续不用，先查价值和流程，不继续堆功能 |
| 成交 | 同一报价范围的报价数、成交数和拒绝原因 | 有效需求不足时调整客群或场景 |
| 交付 | 每单工时、返工次数、恢复成功与支持问题 | 实施工时过高时先做标准化 |
| 续费 | 客户是否愿为持续通知、团队协作或维护付款 | 有明确意愿再投入对应订阅能力 |

首阶段的成功信号是“有客户为明确范围付款，完成验收，之后仍在使用，而且单笔交付成本可控”。Star、浏览量和演示点赞可以参考，但不能代替这个信号。
